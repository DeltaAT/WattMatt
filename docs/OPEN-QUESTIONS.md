blocked. Confirm or overrule them; changes go through an issue.

| 1 | "Grandstand at the end" — what exactly? | Interpreted as **Siegerehrung**: an animated podium showing 1st, 2nd and 3rd place, triggered manually by the host. If a standings *table* of all participants was meant, that is a separate scene and needs its own issue. |

| 20 | Issue #5 adds mutating actions before the undo stack exists | `showScene`, `blackout` and `setAutoFollow` (issue #5) commit without landing on an undo stack, because the stack is issue #11. Assumption: #11 hooks into `TournamentStore.commit`, which is the single funnel every action already goes through, and no action written before then needs changing. If #11 finds it needs per-action metadata instead, these three actions are the first to revisit. **Extended in #9:** `setNewDocument`, `setOpenedDocument`, `setDocumentSaved` and `closeDocument` commit the same way and are on the same footing — the undo box on that branch fails by construction too. One of them is different in kind, though, and that part is *not* deferred: **closing a tournament is not undoable even once #11 lands.** The stack #11 builds is in memory and does not reach across a document switch, so the state undo would restore is the state that was just discarded. The unsaved-changes dialog is therefore the only thing standing between a misclick and a lost tournament, which is why *Verwerfen* is its quietest button and why the flow is tested end to end in `useTournamentDocument.test.tsx` rather than left to inspection. Assumption: #11 does not attempt to make document switches undoable. | 23 | Issue #8 delivers the RNG but two of its bullets land elsewhere | #8 lists "seed generated from `crypto.getRandomValues` at tournament creation" and "persist `rngSeed` and `rngCursor` so a reloaded tournament continues the same stream". Assumption: **#9 calls `generateSeed()` once when creating a tournament and never again, and #16 writes `rng.cursor` back into `rngCursor` on every committed draw.** Until #16 does, acceptance criterion "replaying (seed, cursor) reproduces a full tournament draw-for-draw" is demonstrated only at the RNG level — `createRng(seed, cursorAfterFirstDraw)` reproduces the next draw exactly — not end to end. | 25 | What are the "recent tournaments" on the start screen? | **The default library, listed from disk, newest first** — not a remembered most-recently-used list. Implemented in #9. | 26 | When does a new tournament first reach the disk? | **Immediately on creation**, into the library under a file name derived from its name and made unique against what is already there (#9). Assumption: the host would rather have a file they did not ask for than lose one they did. A write that fails is not fatal: the tournament stays open, the state line reads *Noch nicht auf der Festplatte*, and *Speichern unter…* is the way out. |

| 28 | What does *Änderungen verwerfen* still mean once autosave is running? | **It survives only for a tournament that has never reached disk.** Closing a tournament or the window now flushes the pending autosave first (#10), so a tournament with a file is written before the question would have been asked — and the question is not asked. Reasoning: with a 500 ms debounce, "discard" could only ever discard the last half-second, and offering a host a button that undoes an arbitrary fraction of what they just did is worse than not offering one. The dialog stays for the `unsaved` file state, where closing genuinely loses everything and the app cannot decide on the host's behalf. This narrows the guarantee recorded in #20, which was written before autosave existed. Assumption: undoing a decision is issue #11's job, not the close dialog's. | 29 | Rotating three backups before *every* save makes them minutes apart, not hours | Implemented as docs/FILE-FORMAT.md rule 3 and issue #10 specify: every save rotates, and the acceptance criterion ("backups rotate correctly over 50 consecutive saves") is written on that basis. The consequence is worth stating plainly, because it is not what "three backups" sounds like: during an active round the chain covers roughly the last three autosaves, which can be under a minute of an event. Reasoning: the failure the backups actually defend against is a corrupt or truncated *current* file, and for that the previous three writes are exactly the right thing to hold. Recovering the tournament as it stood an hour ago is not a case anybody has asked for, and would be a different feature — a timed snapshot chain — not a deeper rotation. Assumption: if a host ever does need to go back further, the answer is periodic snapshots under their own names, decided in their own issue. |
| 30 | An autosave failure cannot be dismissed | The `autosaveFailed` notice is the only one in the host UI with no *Ausblenden* button (#10). Reasoning: every other notice reports something that already happened and is over; this one reports a condition that is still true while the host reads it — the stick is still out, the file is still locked — and nothing is being written for as long as it is. A banner they can hide is a banner they will hide, and the next thing they would learn about it is the crash. It clears itself the moment a write succeeds, and it carries *Speichern unter…* so there is always something to click. Assumption: the host would rather lose a strip of screen than lose the tournament. |
| 31 | A save marks the file clean — but the host kept clicking while it was being written | **Only a save whose `documentRevision` still matches marks the file `saved`;** anything else leaves it `modified` and lets the scheduled autosave catch up (#10). Reasoning: the write is asynchronous and the debounce is 500 ms, so during an active round most writes overlap the host's next decision. Marking the file clean regardless would tell them a result is safe when it is not in the bytes on disk — and the crash a second later is exactly the scenario autosave exists for. A second counter was needed rather than reusing `revision`, which also moves for staging a beamer scene and for taking manual control: keying on it would mark a current file unsaved because the host pressed a beamer button mid-write, at the cost of a redundant write and a backup rotation each time. Assumption: no future action mutates `document` without going through `commit`, which is what makes `documentRevision` a complete record of what a file could contain. If one ever does, this guard silently stops working, and so does the dirty flag it sits next to. |
