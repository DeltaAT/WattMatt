# Open Questions

Decisions made with incomplete information. Each has a **current assumption** so work is not
blocked. Confirm or overrule them; changes go through an issue.

| # | Question | Current assumption |
| --- | --- | --- |
| 1 | "Grandstand at the end" — what exactly? | Interpreted as **Siegerehrung**: an animated podium showing 1st, 2nd and 3rd place, triggered manually by the host. If a standings *table* of all participants was meant, that is a separate scene and needs its own issue. |
| 2 | Are matches best-of-one? | Yes. The host clicks a winner; no scores, no sets, no draws. Adding scores later would touch the whole `Match` model. |
| 3 | Can a match end in a draw? | No. A winner must always be picked. |
| 4 | Final phase when fewer than 16 groups remain | The final phase starts at whatever power of two is reached (16, 8, 4 or 2) and names are entered then. A 32-group tournament reaches 16; a 10-group tournament reaches 8. |
| 5 | Is the repechage possible more than once? | No. Only after the qualifying round, because from then on the field is a power of two and halves cleanly. |
| 6 | Who decides accept/decline in the repechage? | The team decides, the host records it. Declining means elimination — the group does not return to the pool (except via the §4 fallback). |
| 7 | Team size / number of players per group | Not modelled. A group is one opaque unit with a number and, later, a name. |
| 8 | Are participant names needed earlier than the final phase? | No, but `settings.namingAt` makes the threshold configurable in case a host wants names from the start. |
| 9 | Sound effects | Out of scope for v1. If added: bundled locally, off by default, host-toggleable. |
| 10 | Multiple tournaments open at once | No. One tournament per window set. Switching files closes the current tournament (with a save prompt). |
| 11 | Repository visibility and licence | Repo created **private**. Licence undecided — add one before making it public. |
| 12 | Code signing the installer | Not planned. Windows SmartScreen will warn on first run; the host manual explains the click-through. |
| 13 | Printing / exporting results | Out of scope for v1. A PDF export of the bracket would be a natural v1.1 feature. |
| 14 | Touchscreen use by the host | Assumed mouse/trackpad. Hit targets are sized generously anyway (≥ 32 px). |
| 15 | The border tokens miss the 3:1 non-text contrast target | `--wm-border` reaches 1.48:1 and `--wm-border-strong` 2.00:1 against `--wm-bg`, against the 3:1 in STYLEGUIDE §1. The palette is implemented **as written** (issue #3) rather than quietly lightened, because the same greys are what keep a dark beamer from looking banded. Assumption: borders are decorative separators and never the only signal — a control that needs a visible edge uses `--wm-accent` or a status colour, both of which clear 3:1. Raising the border tokens is a palette change and needs its own issue. |
| 16 | How much chrome may the single-monitor preview beamer have? | The projected beamer is undecorated, cursorless and unselectable. The **preview** keeps its title bar and its cursor, and carries a `Vorschau` badge. Reasoning: with one screen the preview shares the monitor with the host UI, so an undecorated window the host cannot move or close, that also swallows their only pointer, is a trap rather than a faithful preview. Assumption: nobody in an audience is looking at a preview window, so fidelity loses to usability here. If a venue ever mirrors the laptop screen to the projector, this needs revisiting. |
| 17 | What counts as "a tournament is running" for sleep inhibition? | Currently **the beamer window being open**, because there is no tournament state until issue #5. Assumption: the condition moves to the real one once the store exists — an open beamer over-inhibits at worst, which is the harmless direction. |
| 18 | Which bundle identifier does the app ship under? | `at.deltadeveloping.wattmatt`, changed from the placeholder `at.wattmatt.app` in issue #4. It is not cosmetic: it decides `%APPDATA%\<identifier>\`, which issue #10 autosaves into, and the NSIS upgrade code that issue #31 ships. Assumption: the vendor namespace is correct and settled now, while no tournament file exists anywhere to be stranded — changing it after release would orphan every host's autosave and recovery data. |
| 19 | What does a snapshot carry before the domain model exists? | Issue #5 builds the host → beamer channel, but issue #7 owns the tournament model. The snapshot envelope is therefore final — revision, scene, `autoFollow`, delivery — while its `tournament` field carries only `groups` (id, number, optional name), the one entity already fixed by docs/GLOSSARY.md. Assumption: #7 extends `tournamentSnapshotSchema` in place and leaves the envelope alone. The channel is profiled against 64 groups, but against the placeholder group shape — roughly 3 KB, not the few hundred KB ARCHITECTURE §3 anticipates. The 16 ms number is therefore a floor, not a proof, and is re-measured when #7 lands the real snapshot. **Settled in #7:** the placeholder group shape is gone — the snapshot now carries the real `Group`, so there is one definition rather than two. It still carries *only* groups: the scenes that need rounds, tables and the bracket are #18, #19, #25 and #27, and each extends the schema with what it draws rather than #7 guessing at it. The 16 ms budget still holds at 64 groups, but remains a floor until a scene sends more than groups. |
| 20 | Issue #5 adds mutating actions before the undo stack exists | `showScene`, `blackout` and `setAutoFollow` (issue #5) commit without landing on an undo stack, because the stack is issue #11. The Definition of Done box for undo therefore fails on that branch by construction rather than by oversight. Assumption: #11 hooks into `TournamentStore.commit`, which is the single funnel every action already goes through, and no action written before then needs changing. If #11 finds it needs per-action metadata instead, these three actions are the first to revisit. |
| 21 | FILE-FORMAT.md stored German enum values (`ACHTELFINALE`, `GRUPPE`) | Changed to English (`ROUND_OF_16`, `GROUP`) in issue #7, and the document updated to match. CLAUDE.md golden rule 1 is unambiguous that code is English, and a stored enum value is code — it is compared, switched on and indexed by, never displayed. The German names are UI copy and live in `de-AT.ts` where the glossary says they belong. Assumption: no `.wattmatt` file exists anywhere yet, so this costs nothing now and would cost a migration later. The lint rule cannot catch this class of slip, because `ACHTELFINALE` contains no umlaut — it is caught by review only. |
| 22 | What happens to a group's number when the host removes it during SETUP? | Not decided by issue #7. `GroupStatus` is `ACTIVE \| ELIMINATED` — the tournament lifecycle — and removal is left to issue #14 (group management). TOURNAMENT-RULES §2 requires that numbers are never reused, which a plain delete plus `max(number) + 1` would violate the moment the highest-numbered group is removed and another added. Assumption: #14 picks either a `WITHDRAWN` status or an explicit next-number counter, and that choice is a schema change it owns. Recorded here so it is decided rather than discovered mid-event. |
